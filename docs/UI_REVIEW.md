1. **满屏矩形**——14px 圆角的"面板化外壳"把顶栏、内容区、侧栏分组、卡片统统切成独立圆角盒子，亮色主题下等于 12 个白框套 12 个彩框；
2. **强调色被稀释**——主色同时承担"导航选中""唯一主操作""每本书的进度"三种语义，于是屏幕上一片蓝色横条，比书名还抢眼；
3. **等距代替层级**——卡片内四段内容全是 8px 间距，标题和副标题之间的距离等于封面和标题之间的距离。

下面按维度列问题，再给优先级建议。

## 一、信息架构

### A1 ★ 「最近阅读」一词二义（真实歧义）

侧栏第 2 项是**筛选**：「最近阅读」；顶栏右侧是**排序**下拉，第一个选项也叫「最近阅读」。两者同屏出现、同名、不同语义——用户看到两个一模一样的词，一个在左边决定"看哪批"，一个在右边决定"怎么排"。

- 证据：`.playwright-cli` 截图 shelf-dark / shelf-light，两处文案逐字相同；`Sidebar.tsx:37` 与 `TopBar.tsx:168`。
- 建议：排序项改为「最近打开」「添加时间」「书名」，或给整个排序控件加「排序：」前缀。
- 影响：纯文案改动，零风险，歧义立即消失。

### A2 顶栏 scope 与侧栏激活项重复

`.topbar-scope` 显示当前分类名（"全部"），侧栏激活项也显示"全部"——桌面端同屏两次表达同一状态，且 scope 还带一条 `border-left` 分隔线，把重复信息做成了比侧栏更重的视觉元素。

- 建议：桌面端删除 scope，分类状态由侧栏 + （窄屏时）顶栏下拉承担。
- 影响：顶栏左侧从「☰ 岑序 │ 全部」缩到「☰ 岑序」，右侧搜索框获得更多空间（见 B1）。

### A3 顶栏承载 7 类元素，且被切成三段

顶栏同时有：☰ / 品牌 / scope / 搜索 / 分类下拉（仅窄屏）/ 排序 / 视图切换 / 导入 / 设置。

`components.css:3544` 把搜索框设成 `position:absolute; left:50%`，导致 1440px 宽屏下：左侧「☰ 岑序 全部」与搜索框之间约 260px 空白，搜索框与右侧操作区之间又一段空白。顶栏读作**三条互不相干的带子**，而不是一条操作条。

- 建议：取消绝对居中，改三段式 flex（品牌区固定 / 搜索区 `flex:1` / 操作区固定），搜索框靠左并给明确最大宽度。
- 影响：搜索框不再位于视线正中，肌肉记忆需重建；换来的是顶栏恢复为一条连贯的操作条。若一定要保留居中，至少删掉 scope 并把宽度上限从 26vw 提到 32vw 以压缩两侧空白。

### A4 分类入口在桌面被隐藏

`.topbar-filter { display:none }`（<768px 才显示）。桌面端改分类的唯一路径是侧栏——这本身合理，但配合 A2 的 scope 文本，就出现"顶栏告诉你你在哪，却不能让你改"的不对称。

## 二、视觉层级

### B1 ★ 顶栏内控件的描边强度分了三档

实测计算样式（亮色）：

| 控件 | 描边 | 对比度 |
|---|---|---|
| `.search-box` | `--c-border-strong` #888E97 | 3.30:1 |
| `.topbar-sort` | `--c-border-subtle` #E3E5E8 | 1.28:1 |
| `.segmented` | `--c-border-subtle` #E3E5E8 | 1.28:1 |
| `.topbar-filter` | `--c-border-subtle` #E3E5E8 | 1.28:1 |

**搜索框是顶栏里描边最重的控件**，比唯一的主写操作「导入」还重。视觉权重倒挂：用户第一眼落在搜索框上，而不是"导入"。

> 附带的实现问题：`components.css:2098` 的 `.topbar-sort { border: 1px solid var(--c-border-strong) }` 被更早的 `.topbar select { border: ...subtle }`（`:83`）以更高特异性覆盖（`(0,1,1)` > `(0,1,0)`），实测生效值确为 #E3E5E8。**意图与实现不符**，两条规则应合并为一条。

### B2 ★ 强调蓝一职三用，权重被稀释

实测同屏 `rgb(47,111,235)` 实心元素共 **19 个**：导入按钮 1、视图切换选中块 1、卡片 hover CTA 10（隐藏但在场）、**进度条填充 5 条可见**。

主色同时表示：导航选中态 / 唯一主写操作 / 每本书的阅读进度。语义混用导致"蓝色"不再传递任何确定信息，于是它退化成装饰；而 5 条饱和蓝横线横向排布在网格里，**是整个书架重复度最高、最抢眼的元素，比书名还强**。

好消息：完成态降级逻辑已生效（实测 `100%` 的书进度条为 `rgb(136,142,151)` 灰色，`data-done=Y`），没有 bug。

### B3 书名比全局正文字号还小

`body` 基准字号 `--fs-14` (14px)，而 `.card-title` 是 `--fs-13` (13px)/600，`.card-sub` 是 `--fs-12` (12px)/tertiary。

**书架上最重要的内容被渲染得比应用基准字号更小**，而标题与副标题之间只差 1px + 字重 + 颜色弱化三重叠加，扫视时容易糊成一行灰字。

### B4 悬停 CTA 是全卡最重的元素

`.card-hover-cta` = 32px 高**实心强调蓝**块 + 6px 圆角，出现在每张卡片上。相比之下全局唯一的主操作「导入」是 32px 蓝色实心按钮——两者权重相当，但一个是全局动作、一个是每卡重复动作，重复的那一个不该占同等重量。

## 三、留白与间距

### C1 ★ 卡片内部四段全等距

`.card-target { gap: var(--sp-2) }` = 8px，实测确认。封面 → 书名 → 副标题 → 进度行，**四段间距完全相同**。

后果：书名和它的副标题之间的距离，等于封面和书名之间的距离。没有分组，就没有层级——这是"平铺"而不是"结构"的根源。

建议分组间距：封面 → 书名 12px；书名 → 副标题 4px；副标题 → 进度 10px。卡片总高增加约 6px，现有 24px 行距足够吸收。

### C2 "框中框"

卡片是 `padding:8px` 的白底容器 + 1px 描边 + 13px 圆角，里面的封面又是 9px 圆角。两者只隔 8px，形成"框里再套框"。整屏 12 张书 = 12 个白框套 12 个彩框。

### C3 间距标尺在关键位置混用

`.content` 上下 24px（sp-6）/ 左右 20px（sp-5）；网格 row-gap 24px / column-gap 20px；卡片内 8px 全等距。sp-5 与 sp-6 只差 4px，在宽屏上读不出"节奏"差异，却让间距系统失去可预测性。

### C4 两条互斥的 max-width

`.content-inner { max-width:1440px }` 与 `.shelf-grid { max-width:1680px }` 并存，后者被父级永久约束，永不生效。死规则。

## 四、配色对比

### D1 ★ 亮色下侧栏面板与卡片同白

实测：`.side-panel` bg = `#FFFFFF`，`.card-target` bg = `#FFFFFF`，`.content` bg = `#F3F4F6`。

同一个白色被用在两种语义上，结果是：侧栏 3 个白盒子 + 内容区 12 张白卡，共 15+ 个白块浮在同一片灰底上。`components.css:3441` 的注释说"再加描边就回到文件管理器的样子"——但**去掉描边后白底本身仍然是盒子**，只是从"描边盒"变成了"色块盒"。

### D2 深色 chip 硬编码，浅色封面上发脏

`.card-format` 与 `.card-more` 都写死 `rgba(12,16,22,0.5~0.55)` + 白字 + `backdrop-filter: blur()`。在亮色主题的米色 PDF 封面（`#FCFBF7`）上，"PDF"角标读作一块脏灰斑——hover 截图（`.audit/hover-light.png`）里清晰可见。

同时 `blur(4px)` 在 WebView2 上还有合成开销，而它服务的是一个本可以不用半透明的 chip。

### D3 进度条轨道

`.card-progress-track` 底色 `rgba(0,0,0,0.07)`（亮色）/ `--c-bg-active`（暗色），3px 高，是"不可见但存在"的第三种灰阶——在视觉层级里几乎没有位置。

## 五、字体层级

### E1 UI 层完全没有字体性格

`--font-ui` = `-apple-system, "Segoe UI", "PingFang SC", "Microsoft YaHei", ...`——纯系统栈。阅读层却认真选了 Source Han Serif / Noto Serif CJK。**界面层与阅读层用了两套完全不同的字体策略**，界面层等于放弃了个性。

不建议为此引入完整自定义字体（会明显增大安装包，且中文字体体积敏感）。更经济的做法：只给**品牌字**（"岑序"）和**数字**（百分比 / 页码 / 计数）做特殊处理——这两处是全局仅有的"签名位"。

### E2 字号阶梯在 11–14px 挤了 5 档

`--fs-11 / 12 / 13 / 14 / 16 / 20 / 24 / 30`。其中 12px 与 13px 承担了至少 6 种不同语义（副标题、角标、菜单项、进度数字、选项按钮、设置摘要），角色无法从字号本身辨认。**主内容（书名）反而落在 13px**，是阶梯里偏低的一档（见 B3）。

## 六、组件一致性

### F1 ★ 同一层的两个下拉，一个自绘一个原生

`.topbar-filter`（分类）已改造成自绘 `MenuShell`，`.topbar-sort`（排序）**仍是原生 `<select>`**。作者在 filter 的注释里写过"原生 select 在 Android 上弹出的是系统那套灰底单选列表，和这个应用没有半点关系"——**同样的问题原封不动地留在了排序上**。桌面端弹出的是系统 Win32 下拉列表，与整体风格完全脱节，且原生箭头线宽与自绘 chevron 不一致。

`MenuShell` 组件现成可用（`src/components/shelf/MenuShell.tsx`），TopBar 里已经在用它渲染分类菜单，接入成本约 30 行。

### F2 同一张卡片上三种 chip 风格

`.card-format` / `.card-more` 是硬编码深色半透明 chip，`.card-badge`（文件已丢失 / 待恢复）却是 `--c-bg-surface` + `border-subtle` 的浅色 chip。同一张卡片上并存两套 chip 语言。

### F3 同一类按钮在不同容器反馈不一致

`.btn-primary` 在设置抽屉里悬停会上浮 1px（`transform:translateY(-1px)`），但在顶栏被 `.topbar .btn:hover { transform:none }` 特判掉。**同一个组件、同一个主操作，在两个容器里手感不同。**

### F4 `.icon-btn[data-active]` 三层蓝

设置抽屉打开时，齿轮按钮同时叠加：`--c-bg-selected` 底 + `inset 0 0 0 1px var(--c-accent)` 描边 + 键盘焦点环（2px outline，`--c-border-focus` 与强调色同色）。三层同色叠加，且焦点环色与强调色相同，会与"激活态"混淆。

## 七、交互反馈

### G1 ★ 触屏上「更多」按钮永久不可见

`components.css:2988` 的 `@media (hover: none)` 明确把 `.book-card:hover .card-more { opacity: 0 }` 写死；而 `.card-more` 本身 `opacity:0`，只在 `:hover` / `:focus-visible` 时置 1。

**结论：Android 端用户永远看不到「更多」按钮。**唯一路径是长按 450ms，而卡片上的 `title` 属性写的是**书名**（`BookCard.tsx:78`），没有任何长按提示。触屏用户实际上无法发现"重命名 / 移动 / 删除 / 重新定位"这些操作。

同一规则下 `.card-hover`（"继续阅读 · 42%" 浮层）也永久不可见——移动端没有任何悬停态的补偿。

### G2 格式角标在悬停时消失

`.book-card:hover .card-format { opacity: 0 }`。信息在"静止"时出现、在"用户产生意图"时隐藏，逻辑倒置——而且 hover 截图确认 PDF 角标确实消失了。

### G3 浅色封面上的悬停遮罩过重

`.card-hover` = `linear-gradient(to top, rgba(8,11,16,0.88) 18%, rgba(8,11,16,0.52) 58%, transparent)`，峰值 88% 近黑，从封面底部往上吃掉近一半高度。浅色封面上形成一条**硬黑带**（`.audit/hover-light.png` 中的"建筑十书"最明显），与注释里"不遮住上半张封面"的意图有落差。

### G4 触控命中区偏小

`.card-hover-cta` 28px、`.card-more` 24×24、`.search-clear` 16×16。桌面鼠标场景可接受；触屏建议 ≥36px（44px 是通用基线，当前远未达到）。

## 八、响应式体验

### H1 搜索占位符按 UA 切换，不按宽度

`IS_MOBILE` 基于 `navigator.userAgent`（`src/lib/platform.ts:7`）。桌面端把窗口缩到 800px，占位符仍是"搜索书名或作者"，会把本来就窄的搜索框挤成省略号。建议改由 CSS 媒体查询或容器查询控制。

### H2 列表视图在移动端丢掉进度

`<768px` 时 `.shelf-row .row-progress { display:none }`，`.row-cell` 也隐藏。移动端切到列表视图后**完全看不到阅读进度**，只能看到书名和类型。

### H3 1199px 折叠侧栏后信息量骤降

768–1199px 侧栏收成 64px 纯图标条，依赖原生 `title` 提示（延迟约 1s、样式不统一）。可接受，但折叠后失去计数信息（`.sidebar-count` 被隐藏），用户无法在窄窗口判断各分类的存量。

### H4 移动端顶栏偏挤

390px 下：搜索框 + 分类下拉(84px) + 「导入」实心蓝按钮 + 齿轮。搜索框被压到约 140px。移动端优先级建议为 搜索 > 分类 > 导入——「导入」在移动端已有空状态入口和拖拽层，可考虑在窄屏降级为图标按钮，把空间还给搜索。

# 按优先级排序的优化建议

## P0 · 立刻改（决定"通透感"成败）

| # | 改动 | 为什么提升现代感 / 通透感 | 可能产生的影响 |
|---|---|---|---|
| **P0-1** | **卡片去框**：`.card-target` 去掉背景、描边、内边距；封面圆角 9→12px；文字直接落在页面底色上；悬停时只让**封面**浮起（阴影 + 1.02 scale），文字区不动 | 一屏里 12 个"白框套彩框"归零。页面底色成为唯一背景，封面成为唯一"物"——这正是现代阅读器（Librum / Apple Books / Notion Gallery）的处理方式。层级不再靠盒子堆叠，而靠"图浮在纸上" | 亮色下卡片与内容区失去"实心白"的底色差，改由封面自身 + 悬停阴影分层；`.card-target:focus-visible` 必须改成把焦点环画在**封面**上，否则键盘用户看不到焦点在哪。`.card-ring` / `--shadow-card` 需要重新校准 |

## 执行建议

**建议节奏**：P0 六项一次做完（约 3–4 天），它们共同决定"通透"能否成立——单做其中一两项效果会被其余项抵消。P1 第二批（约 3–4 天）。P2 随版本零散收。

**验证方式**：项目已有 `src/lib/devMock.ts`，`npm run dev` 即可在浏览器里跑全套界面并截图核对，无需打包。改完后建议：
1. `npx tsc --noEmit`
2. 亮/暗双主题 × 1440×900 / 390×844 四张截图对比
3. 重点复核 P0-1 的**键盘焦点环**（焦点必须落在封面上）与 P0-3 的**排序下拉键盘导航**

**风险提示**：P0-1（卡片去框）会改动 `.card-target` 的盒模型与阴影体系，是本批中影响面最大的一项，建议单独一次提交并单独截图验收；P0-3（排序改自绘）会新增一段 MenuShell 接入逻辑，注意保留 `aria-haspopup` / `aria-expanded` 与点外关闭行为。

**不受本轮影响的部分**：阅读层（`reader.css` / 阅读页）实测排版干净、克制，符合"书架层丰富、阅读层克制"的既定原则，不建议在本轮改动。
