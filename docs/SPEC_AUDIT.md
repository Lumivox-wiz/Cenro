## 三、冲突已裁决

**双页封面位置（UI §6.3 / UX §7.2）**

规范要求封面「单独显示在右侧（日漫）/ 左侧（西漫）」；此前实现固定为居中。

**裁决结果（2026-11-12，用户确认）**：改为用户可选，设置 → 阅读 → 双页封面：

| 选项 | 行为 | 默认 |
|---|---|---|
| 居中 | 封面单独一屏、半宽居中 | ✅ 默认 |
| 靠边 | 日漫靠右、西漫靠左（符合规范 §6.3） | — |

末页单张始终按阅读方向靠边，不受该选项影响。

默认值取「居中」是因为用户在实测中两次明确要求居中；规范 §6.3 允许用户手动选择优先于自动判断，此处按同一精神处理。切到「靠边」即为完全合规状态。

| 命中项 | 位置 | 处理 | 理由 |

| 全大写 + 宽字距 | `.shortcut-help-section-title` 0.08em | ✅ 删 `text-transform` 与宽字距 | 标题是中文，uppercase 无效，宽字距只把字组散开 |

| 阴影带蓝调 | `.segmented-item[aria-pressed]`、`.card-cover`、亮色 `--shadow-card` `rgba(16,24,40,·)` | ✅ → `rgba(0,0,0,·)` | 中性阴影里混蓝，暗色下底层偏冷 |

## 七、观感层复核（2026-11-16，v0.15.2）

| 暗 次级 / 面板 | 6.68 | ✅ |

| 亮 强调字 / 白 | 5.21 | ✅ |
| 亮 实心按钮底 / 白字 | 4.57 | ✅ 下限 |
| **亮 白卡 / 页面底** | **1.10** | ⚠️ 无层次 |

文字层全部达标，问题都在「面与面之间」。据此改了五处，逐项登记：

| 白卡无层次 | `--shadow-card`、`.card-target` | 亮色阴影改为三层（近距 `.06` + 中距 `.05` + 远距 `.32/-18px`）；卡面补 `--c-card-ring` 描边 |

**冲突已裁决**：`.card-target` 原注释写着「不给每个元素描 1px 灰线——白底上只有 1.2:1，等于没画」。
该判断本身成立，但它回答的是「描线能否代替分层」，而实测暴露的是「两个面根本没分离」。
故改为「阴影负责抬起、极淡描边负责切边」，注释已同步改写，未静默覆盖原决定。

**新增 token**：`--c-card-ring`、`--c-cover-ring`，暗色在 `tokens.css`、亮色在 `themes.css` 一一对应。

### 对比度实算（最坏情况：纯白 PDF 封面从顶栏下经过）

浏览器按 **sRGB 空间**合成（不是线性空间），这点决定了 alpha 能放多低：

- 暗色 `rgba(30,33,40,0.70)` 压纯白 → ≈ `#5D5D5F`，`--c-text-primary #E6E8EB` 对它 **5.3:1**（AA 过）

- 反解下限：暗色 alpha < 0.66 时，最坏情况掉到 4.5 以下 → **0.66 是硬下限**，规范已写死

1. **亮色下纯白封面经过时，顶栏带子也接近纯白**，搜索框（`--c-bg-surface` 同为白）只剩 1px 描边可辨。

3. `--glass-header-*` 与 `--glass-*` 现在是两套值，理由写在 `UI_SPEC §2.9.1`；

## 十三、侧栏选中块悬浮（2026-11-16，v1.7）

用户指着侧栏问「这些高亮选中的能不能做悬浮」。

### 改了什么

| 项 | 改前 | 改后 |
|---|---|---|
| 选中块 | 平涂 `--c-bg-selected`（10~15% 蓝），无阴影 | 加 `--shadow-chip`（贴纸投影 + 顶部 1px 内高光），读作浮起约 1mm 的薄片 |
| 悬停 | `--c-bg-hover`，无阴影 | 加 `--shadow-chip-hover`（半档），保持明显弱于选中 |
| 过渡 | 只有 background / color / transform | 补 `box-shadow`，切换分类时不「闪」一下 |
| 触屏 | `hover:none` 只复位了卡片与列表行 | 补 `.sidebar-item:hover:not([aria-current="true"])` —— 否则点过的那格会变成第二枚「选中块」 |

### 为什么不做成玻璃

侧栏背后是纯色纸面，blur 什么也透不出来（`UI_TRANSLUCENCE_PLAN §2.3` 同一条结论）。
选中块要的是「离开纸面 1mm」，不是「透出后面的东西」——所以用阴影，不用材质。

### 验收

- 计算样式：选中 `box-shadow` 三段（1px 3px / 10px 22px -10px / inset 1px 高光）✅
- 悬停 `box-shadow` 为单段 `0 1px 2px`，明显弱于选中 ✅
- 暗色下内高光用白 8%，投影用纯黑；亮色内高光白 90%，投影用 `#101828` ✅
- 1440 / 900 / 393 三档无溢出；侧栏 `overflow:hidden` 未裁到投影（左右留白 8px ≥ 水平扩散）✅

### 遗留

## 十四、窄窗信息补齐（2026-11-16，v1.8 · 第五批）

`UI_REVIEW` 里剩下的四条 H 组问题，都属于「窄窗/手机上信息直接消失」，
不是审美问题而是可用性问题。另外在核查时挖出一处**从 v1.4 就存在的布局 bug**。

### 做了什么

| 项 | 改前 | 改后 |
|---|---|---|
| H2 列表进度 | `<768px` `.row-progress` 整列 `display:none`，手机上列表只剩书名 | 百分比挂到书名行末尾，`margin-left:auto` 右对齐；状态标签仍紧跟书名 |
| H3 折叠态计数 | `.sidebar-count` 在折叠态与 768–1199px 都是 `display:none` | 纵向堆叠：图标在上、数量在下，条目 40 → 46px |
| H4 移动端顶栏 | 「导入」保留文字，393px 下吃掉约 30px | 降级为 32×32 图标按钮，搜索框 140 → 205px |
| H1 占位符 | `IS_MOBILE`（UA）判断 | `matchMedia("(max-width:767px)")`，与布局断点同源 |

### 顺带修掉的既存 bug

`components.css` 里「窄窗收起类别列」那条是 `@media (max-width: 1199px)`，
位置在 `767px` 段**之后**，同特异性把移动端的
`grid-template-columns: 40px minmax(0,1fr)` 整条覆盖成 5 列
（`40px 0px 96px 120px 140px`），标题所在列被压到 **0 宽**。

实测：`.row-title` 宽度 `0px`、`.row-title-text` 宽度 `0px`，
而 `.row-cell` / `.row-progress` 已经被隐藏——于是整行只剩封面，**连书名都没有**。
这不是本次改出来的：`UI_REVIEW` 写「移动端切到列表视图后完全看不到阅读进度，只能看到书名和类型」
的前提本身就是错的。

修法：媒体查询补 `min-width: 768px` 下界，让 767 与 768–1199 两段互斥，
先后顺序不再影响结果。

### 一处反复（记下来免得再走一遍）

H3 最初做成**右上角角标**（`position:absolute; top:5px; right:2px`，9px）。
实拍三档后否掉：这一列全是 lucide 的 2px 描边线性图标，**没有干净的角**——

读作散落的点，且圆形图标（时钟）旁边尤其像悬空。

最终改纵向堆叠：图标在上、数量在下，两者都严格居中，零重叠。
代价是条目从 40px 长到 46px（8 项共 +48px，700px 高的窗口仍放得下）。
`[data-sidebar="expanded"]` 那段顺手补齐了 `height` / `flex-direction` 复位——
只改 `display` 会留下「横向排版 + 折叠态字号」的混合态。

### 验收（`npx tsc --noEmit` + `vite build` 通过；playwright 实测）

| 视口 | 探针结果 |
|---|---|
| 1440 展开 | 侧栏 240px、条目 40px、`flex-direction: row`、标签显示、计数 11px 静态 ✅ |

### 遗留

1. 折叠态「添加目录」没有计数，纵向堆叠下它与上面几项的视觉重心差约 5px（无数字可居中）。

## 十五、书架自定义背景 + 莫奈取色（2026-11-16，v1.9）

用户提出「给主页增加自定义背景功能和主题莫奈取色」，参照两张同类软件的设置面板截图。

### 做了什么

| 项 | 内容 |
|---|---|
| 背景图 | 选图（系统对话框）→ 路径存 prefs → asset 协议加载；填充方式 / 不透明度 10–100% / 模糊 0–40px / 纸色遮罩四个可调 |
| 莫奈取色 | Rust 侧解码 + 降采样 + 色相直方图 → 返回色相与饱和/明度；前端按当前主题派生 8 个 CSS 变量 |
| 设置入口 | 新增「背景」分组（紧跟「主题」），含图片区 + 四个控件 + 取色区 |
| 持久化 | `prefs.background` / `prefs.monet`，`loadPrefs` 做**嵌套深合并**——v1.9 之前存的 prefs 没有这两个键 |
| 预览 | 设置页直接列出浅色 / 深色两套派生色（强调色 / 文字版 / 选中底 + 十六进制） |

### 三个设计决定

**1. 取色只接管强调色一族，不碰纸面与文字**

接管 8 个变量：`--c-accent` / `-text` / `-hover` / `-subtle`、`--c-bg-selected`、
`--c-border-focus`、`--glow-a` / `--glow-b`。

不接管 `--c-bg-app` / `--c-bg-surface` / `--c-text-*`。理由不是保守，是算不出来：
一张偏黄的背景图会让 `--c-text-secondary` 对纸面从 4.8:1 掉到 3:1 附近，
而**每张图掉得都不一样**，不存在一组"跟着图变但永远达标"的映射。
能自动保证的只有强调色：它的对比度是拿在手里算的（图形 3:1 / 文字 4.5:1）。

**2. 取色放后端，不放前端 canvas**

背景图经 asset 协议加载属于另一个 origin，画到 canvas 上会被 taint，
`getImageData` 直接抛 `SecurityError`。后端已有 `image` crate，
顺手把降采样（72×72）也做了，省掉把整张大图塞进 JS 内存。
命令必须 `spawn_blocking`：4K 图解码要两三百毫秒，同步命令会卡住 UI 线程。

**3. 背景图只作用于书架**

阅读页与 `.app-shell` 平级，结构上就进不去。这是刻意的：
正文纸面一旦有图，"透过一层纱看字"的疲劳是累积的，而且没法用遮罩救——
遮罩压到能读的程度，图也就看不见了。

### 一处踩坑（记下来）

`.shelf-bg-layer` 是 `position:absolute; z-index:0`，`.shelf-body` 原本是 static。
按 CSS 绘制顺序，**定位元素整体画在非定位的正常流内容之上**——
于是背景层盖住了侧栏的图标与标签，只有 `.sidebar-item[aria-current="true"]`
（带 `position:relative`）逃过一劫，表现成「侧栏只剩右对齐的计数」。

第一次截图时差点判成「折叠态样式串了」，实际是层级问题。
修法：`.shelf-body { position:relative; z-index:1 }`，顶栏仍是 4、浮层仍是 100。

### 顺带修的两处

| 问题 | 处理 |
|---|---|
| 背景图开启时抽屉/菜单的玻璃变成"背后有照片的毛玻璃"，12~13px 设置文字整体发虚 | `[data-shelf-bg] .glass` 退成 `--c-bg-elevated` 实色；标记同时写到 `<html>`（抽屉挂在 `.app-shell` 之外） |
| 没选图时四个控件仍可拖，拖了没有任何效果 | `fieldset disabled` 一次性收掉 range / button / checkbox；滑块单独改灰（`.slider` 的拇指用 `--c-accent`，不会被原生禁用样式影响） |

### 验收

- `npx tsc --noEmit` ✅ / `npx vite build` ✅（424 kB 主包，无新增依赖）
- `cargo test --lib` ✅ 96 项通过，含新增 3 项：HSL 已知值、灰阶图无色相、**端到端**（写一张纯蓝图断言 hue≈221 且 coverage>0.95，再写纯灰图断言 coverage=0）
- 图层探针（playwright 计算样式）：
  - 未设背景：无图层、`.content` 仍为 `rgb(243,244,246)`、`data-shelf-bg` 不存在 ✅
  - 已设背景：图层存在、`content` 变透明、`app-shell[data-shelf-bg="true"]` ✅
  - 不透明度 45 + 模糊 18：`opacity 0.45`、`filter blur(18px)`、`object-fit cover` ✅
  - 莫奈开：亮色 `#cc701e` / 暗色 `#e69956`（同一色相 28°，两套不同明度）✅
  - 莫奈关：变量回落到主题默认 `#2f6feb` / `#5b8def` ✅
- 视口：1280 / 393 两档，抽屉与书架均无横向溢出 ✅
- 顶栏玻璃在背景图上正常（滚动后 `opacity 1`、`rgba(255,255,255,0.7)`）✅

### 遗留

1. **真实 Tauri 环境未跑过**：dev 下背景图是内联 SVG、取色是 devMock 固定值，
   真实文件路径 + asset 协议 + Rust 解码这条链只在单测层面验证过（纯蓝图那张）。
2. **大图性能未测**：`image::open` 是全解码，一张 8000×6000 的图可能要 500ms+。

   若后续嫌慢，可改用 `ImageReader` + 按需缩放到 72px 的解码路径。
3. **取色对"多主色图"只取一个色相**：直方图峰值桶 + 左右各一桶。
   一张蓝橙对半的图会得到两者中权重更高的那个，不会混合（混合出来一定是脏色，这是刻意的）。

## 十七、连续曲率圆角（2026-11-17，v1.11）

用户要求「UI 圆角改为连续曲率圆角」。

### 用了什么

原生 `corner-shape: squircle`（Chromium 139+），不是 JS 绘图、不是 SVG mask。

理由：`border-radius` 的圆弧在直边相接处曲率突变（0 → 1/R），连续曲率要的就是把这一段
换成 superellipse。CSS 原生方案能跟随任意尺寸与响应式，而 `clip-path: path()` 写死 px、
`clipPathUnits="objectBoundingBox"` 又会让圆角随宽高比变形。

实测环境：WebView2 **157.0.4341.46**，`CSS.supports("corner-shape", "squircle")` 为 true。

### 两个必须一起做的事

**1. 半径要补偿，否则全部控件变「方硬」**

`squircle` = `superellipse(2)`，曲线比圆弧更贴直角，**同样数值下视觉圆角缩水 35~40%**。

第一版按 20~25% 估的（9→10 / 16→18），并排实测后被推翻：10px 连续曲率放在 9px 圆弧旁边
明显更小更方，看起来像"退步"。改用四档并排（9 圆弧 / 10 / 14 / 18）比对后定的补偿量：

| Token | 基准 | 连续曲率 | 说明 |
|---|---|---|---|
| `--r-sm` | 6px | 8px | 输入框、标签 |
| `--r-btn` / `--r-md` | 8px | 11px | 按钮、导航项、侧栏选中块 |
| `--r-cover` | 9px | **13px** | 封面：9→10 不够，13 才回到原来的饱满度 |
| `--r-lg` | 13px | 16px | 菜单 |
| `--r-xl` | 16px | 20px | 抽屉、对话框 |

不是统一乘系数：小控件（按钮、输入框）圆角本来就接近半高，按比例放大会直接变胶囊，
所以只加 2~3px；封面、抽屉这类大元素空间富余，加得多。

**2. 补偿值必须写在 `@supports` 里，不能直接改 `tokens.css`**

一度把补偿值直接写进 tokens，随后发现降级会翻车：不支持 `corner-shape` 的环境
（Android 老 WebView）会拿到「大半径 + 普通圆角」，比 v1.10 更圆。
现在基准值留在 tokens，补偿值在 `global.css` 的 `@supports` 块内覆盖——
支持则「squircle + 补偿」，不支持则「圆角 + 基准」，两边看到的圆润度是同一个。

### 真圆必须排除

`.empty-icon`（64px 圆底）、`.pin-dot`、`.slider::-webkit-slider-thumb`、
`*::-webkit-scrollbar-thumb` 显式 `corner-shape: round`。
超椭圆会把正圆变成略方的形状——12px 看不出，64px 能看出。

### 验收

| 项 | 结果 |
|---|---|
| 计算样式 | `.card-target` → `corner-shape: superellipse(2)`；`--r-sm 8px / --r-btn 11px / --r-cover 13px / --r-xl 20px` ✅ |
| 视觉（4× 裁切） | 封面 9→13px、抽屉 16→20px 与改造前的普通圆角圆润度对齐，过渡更顺 ✅ |
| 整屏（亮/暗） | 封面、按钮、搜索框、侧栏选中块、菜单、对话框均无「切角」违和 ✅ |
| 降级 | `@supports` 不匹配时基准值 + `round` 全部生效，等同 v1.10 ✅ |
| 性能 | 滚动 90 帧：开 3.44ms / 关 3.38ms（+1.8%），p95 4.1 vs 3.3ms ✅ |

### 遗留

1. **`superellipse(1.5)` 虽然当前 Chromium 接受，但规范只定义整数**，未采用；
   若未来想减弱「变方」感，这是唯一的中间档，但要接受它在别的引擎里被拒（落回圆角，不会崩）。
2. **Android 真机未验证**：系统 WebView 若低于 139，效果与 v1.10 完全一致（普通圆角），
   不会出错，但也就看不到连续曲率。
3. 20px 的抽屉/对话框已经接近「苹果图标」那种饱满感；再往上（24px+）在 440px 宽的对话框上
   会开始显得过圆，且与卡片 13px 的节奏脱节，不再加。

## 十九、液态玻璃材质（2026-11-18，v1.13）

需求：给应用增加一个「液态玻璃」主题。

### 结论先行：能加，但**不能做成主题**

`data-theme` 是 `light | dark`，`resolveAppTheme()` 的返回类型、`themes.css` 里亮色那 70 行
变量、以及所有 `[data-theme="light"]` 选择器都绑在这个二值契约上（规范 §3.1）。
把液态玻璃塞进去当第三值，会得到三个坏结果：

1. 亮色变量要整份复制一遍——液态在亮色下也要有「白玻璃」；
2. **「液态 + 暗色」再也组合不出来**，而这恰恰是最该有的一组；
3. `ReaderTheme = "follow"` 的解析逻辑要走一条新分支，阅读层的继承关系表要改。

所以做成**材质**：`data-material="liquid"`，与 `data-theme` 正交。
一个枚举管颜色，一个属性管表面构成，各管各的。

### 现状盘点：玻璃地基早就铺完了

动工前先查了实现，发现不需要从零建：

| 已有 | 位置 | 结论 |
|---|---|---|
| `--glass-*` / `--glass-header-*` 两套 token | `tokens.css` §2.9 | 直接复用，只覆盖值 |
| `.glass` 类 + `@supports not` 降级 | `components.css:728` | 降级主路径已就位 |
| 顶栏 `blur(18px) saturate(1.35)` | `components.css:4020` | 已玻璃化，只需加强 |
| 外壳拍平（顶栏无底色 / 侧栏透明） | v1.6 | **玻璃生效的前提已满足** |
| 内容区光晕 `--glow-a/b` | v1.9 | 加一个覆盖即可 |

也就是说，`UI_TRANSLUCENCE_PLAN.md` 里「方案 B（拍平 + 顶栏玻璃）留作后续专项」
这件事已经被 v1.7/v1.10 做掉了。本轮是在既有地基上加材质层，不是重做外壳。

### 本轮唯一的新判断：棱边必须独立于带 opacity 的层

第一版把镜面高光写进 `.topbar::before` 的 `box-shadow`，截图出来几乎看不出变化。
原因：`::before` 承担模糊与底色，静止态 `opacity: 0.55`、滚动升到 1（v1.10 的机制）。
**高光跟着 opacity 一起被衰减了**——0.2 的 inset 白 × 0.55 ≈ 0.11，
在 1440px 宽的通栏上只剩一条灰线，玻璃退化成色带。

改成独立的 `.topbar::after`（不参与 opacity），高光按玻璃本身的样子呈现，
静止态也能读出「这是一层浮起来的栏」。

**这条要写进规范**（已进 §3.5），因为它不是顶栏专属问题：
任何「父层带 opacity、子层想画高光」的组合都会踩。

### 落点与取舍

| 落点 | 做法 | 为什么 |
|---|---|---|
| 顶栏 | `::before` 模糊 + `::after` 棱边 | 唯一有背后内容的常驻 chrome |
| `.glass` 浮层 | 加折射扫光（`background-image`） | 液态与毛玻璃的观感差别主要在这里 |
| 卡片封面 | `::after` 棱边 + 冷/暖色散 | 整屏面积最大，液态必须在这里被看见 |
| 卡片封面 | **不加 backdrop-filter** | 30 本 = 30 个离屏合成层，WebView2 掉帧；封面不透明，透不出东西 |
| 纸面 / 正文 | **完全不加** | `--c-bg-reader` 必须纯色，渐变会让正文像浮在彩板上 |
| 侧栏选中块 | 只加棱边，不加模糊 | 常驻结构不是浮层 |

**为什么卡片封面一定要做**：书架是停留最久的一屏。液态如果只出现在顶栏和抽屉，
作为主题就是失败的——用户日常根本看不到它。给封面加棱边与扫光是纯合成操作，
零滤镜成本，却能让人一眼看出「换了材质」。

### 降级

液态的变量覆盖**整段包在 `@supports (backdrop-filter: blur(1px))` 内**。

不包会出事：`--glass-bg` 的降级靠组件里的双写（先 `-fallback` 再 `-bg`）
加 `@supports not` 块强行拉回实心。液态段若在外面裸写降了 alpha 的 `--glass-bg`，
不认模糊的内核照样读到它 → **透明度生效、模糊不生效**，背后文字直接和浮层文字打架。
包进 `@supports` 后，「支持」与「不支持」两块互斥，不可能同时命中。

`--glass-bg-fallback` 在液态下**不动**（alpha ≥0.94），它是降级路径的实心底。

`prefers-reduced-transparency` 作为增强路径保留（原有机制，未改动）。
主路径仍是能力检测——WebView2 109 不认这个媒体查询（需 118+）。
